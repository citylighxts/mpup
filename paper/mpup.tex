\begin{abstract}
Retrieval-Augmented Generation (RAG) systems rank passages by topical relevance, yet relevance and usefulness are not the same thing. Even a passage that matches a query may fail to help the model answer. Recent utility-aware RAG methods proven to be impractical because existing methods either fine-tune a reranker or retriever’s embedding model for every target LLM, or run the target LLM on every candidate passage at selection time, which takes up high cost, memory, and computation. Meta-Probing Utility Predictor (MPUP) is a method to predict LLM-specific retrieval utility without fine-tuning the target model.

MPUP turns each query--passage pair into 14 inexpensive features: retriever scores, passage statistics, entity overlap, an NLI check against a hypothetical answer, and the change in the next-token entropy of one LLM caused by the passage. One more score comes from a ridge probe on the hidden states of the same LLM. Passages are ranked by a small regressor trained on within-query deviations, and the target LLM is never fine-tuned. On eleven question-answering datasets labelled with the true utility, run end to end on one Apple M5 laptop with Qwen2.5-7B-Instruct in 4-bit precision (peak memory 6.4 GiB), and with the predictor selected by nested leave-one-dataset-out, MPUP reaches a within-query Spearman correlation of 0.37 with the true utility, against 0.11 for BM25 and 0.28 for dense similarity. The paired gain over dense similarity is $+0.08$ (95\% CI $[+0.05, +0.11]$, $p<0.001$, standardised effect $d_z=0.22$); without the hidden-state probe it is $+0.02$ and not significant. Placing the single passage chosen by MPUP in the prompt raises answer accuracy from 0.360 (dense similarity) to 0.414, while a perfect ranker would reach 0.577. The earlier run in bfloat16 on a GPU, before the probe was added, gained $+0.04$.
\end{abstract}

\section{Introduction}
Large language models (LLMs) are Transformer-based neural networks pre-trained on massive unlabeled text so that they are adapted to specific tasks through prompting rather than task-specific retraining~\cite{min2023}, making one model can do reasoning, summarization, and generation tasks that previously require separate architectures~\cite{chang2024}. LLMs are used in multiple areas, one of them is LLM for personalized tutoring and automated feedback in education~\cite{kasneci2023}. LLMs can also be used in reshaping professional practice, research workflows, and policy~\cite{dwivedi2023}.

LLMs often produce hallucinations which are outputs unfaithful to the source or factually incorrect~\cite{ji2023}, because their knowledge is stored and frozen at training time, making them cannot be corrected without retraining~\cite{huang2025}. Retrieval-Augmented Generation (RAG) addresses this problem by retrieving relevant documents from external sources and do generation on that retrieved evidence, so the model draws on up-to-date information instead of only memorized parameters~\cite{fan2024}. RAGs have multiple methods to retrieve the documents, one of them is traditional RAG which select documents purely by topical relevance where the contents match the queries, which works worse than RAG systems where the documents are selected by their utility for the model~\cite{zhang2026}.

Selecting documents or passages based on their utility in RAG is done by seeing whether the passage providing it as evidence measurably improves a LLM's ability to generate an accurate answer compared to answering without any evidence~\cite{zhang2026}. To measure this, two cases need to be compared. In the first, the model answers from its internal memory alone. In the second, the same model answers with a specific retrieved passage available to it. Both answers are scored by a standard correctness metric, and a passage counts as useful only when the second answer is more accurate than the first. Applying the same test to a large pool of candidates leaves only the passages that actually help that model~\cite{zhang2026}.

However, how can a practitioner estimate passage utility under realistic, low-budget conditions? Existing methods are too expensive for practical deployment, because they require a 32-billion-parameter teacher model to produce supervision~\cite{zhang2025b}, completely retraining the retriever's embedding model using complex objectives~\cite{sandhu2026}, or running the target LLM twice for every single query~\cite{zhang2025c}.

There are cheap alternatives method compared to LLM sampling. Semantic Perplexity (SePer) measures how useful a retrieved passage by observing how much its semantic perplexity changes after the passage is provided, but it still requires running an evaluation model, which adds computation and latency, making it less suitable for real-time passage selection~\cite{dai2025}. Another approach proposes a lightweight neural model that predicts passage utility for a target Question Answering (QA) model, but its predictor is trained for a specific QA model, making it difficult to apply to other QA models~\cite{perez2025}. Another method is a feature-based predictor combining Query Performance Prediction (QPP), perplexity, readability, and document quality features using linear regression to predict retrieval utility, but this method achieves relatively low accuracy for utility prediction, with Spearman $\rho \approx 0.20$--$0.24$ for retrieval utility on Natural Questions~\cite{tian2026}. Low accuracy and unapplicable solutions show that none of these methods has solved the problem yet.

Several other methods have been explored. There are LURE-RAG which introduces a lightweight LambdaMART reranker trained with a listwise utility loss to optimize context ordering, but relying on complex listwise utility supervision requires generating query and passage combinations, making the labeling cost expensive~\cite{chandra2026}. Another approach is RRPO, where passages selection treated as a sequential decision process trained via reinforcement learning directly from LLM feedback, which also which takes up big part of the memory and computation~\cite{wu2026}. Existing methods either require substantial memory and computational resources, or incur high costs.

Meta-Probing Utility Predictor (MPUP), proposed in this paper, closes the gap. MPUP is a method to predict LLM-specific retrieval utility which means it can select the most useful passages for models without fine-tuning any model. Instead of having the target LLM answer with and without every passage~\cite{zhang2025c} or scoring each passage with a separate evaluation model~\cite{dai2025}, MPUP evaluates a passage’s usefulness by looking at 14 practical clues, such as document statistics, meaning overlap, and agreement with a hypothetical answer. Only three of them read the logits of an LLM, through one forward pass per passage (logit probing). MPUP runs its two LLM-based steps, one short generation per query and the probing pass, with one shared model on a single GPU and does not train any LLM. Section IV reports the measured memory footprint and extraction time.

Contributions of this paper are threefold. The first is that many cheap features, used together, rank passages by true utility better than the retriever's own score (BM25) and slightly better than a strong dense-similarity baseline, without a utility-specific model and without having an LLM generate an answer for each passage. Compared with dense similarity, the gain is small, and we report it with confidence intervals. Execution on a single GPU is also possible, and the measured peak memory is reported in Section IV. The second is a predictor that is trained once and is not retrained when the LLM that answers the question changes. Training and evaluation use one source LLM at a time, so transfer to other target LLMs is not tested in this paper. The third is that the predictor can also be trained on annotations that already exist in the dataset, which are cheaper than labels produced by running the target LLM over every passage~\cite{zhang2025a}. Trained this way, the predictor beats BM25 on nine of eleven datasets but not dense similarity.

Remaining sections are organized as follows. Section II reviews related work on retrieval-augmented generation, utility-based passage selection, and lightweight utility prediction. Section III describes the proposed Meta-Probing Utility Predictor, covering the 14 features, the predictor architecture, and the model and hardware setup. Section IV presents the experimental setup, datasets, and evaluation metrics, followed by the results and analysis, while Section V concludes the paper and outlines directions for future work.

\section{Literature Review}
LLM can only use the knowledge it learned during training, and this knowledge cannot be updated without retraining. RAG solves this by first retrieving documents from an external source, then ask the LLM to write its answer based on those documents~\cite{fan2024}. In traditional RAG, passages are chosen by relevance, which means how closely their content matches the query.

However, a relevant passage is not always a helpful one. Recent work shows that choosing passages by their utility for the model gives better results than choosing them by relevance alone~\cite{zhang2026}. Utility is measured by comparing two answers from the same LLM. The first answer is written from the model’s own memory. The second is written with the candidate passage. Correctness metric scores both answers, and the passage is useful only if the second answer is more accurate~\cite{zhang2026}.

Utility also depends on what the model already knows. Passage may help one LLM but add nothing for another LLM that already knows the answer. So, utility belongs to a pair of passage and model, not to the passage alone. To estimate it in practice, we can either test the target LLM directly or approximate it with cheaper signals.

Methods that estimate passage utility can be grouped into four types. Utility estimation by large models or utility-trained retrievers is the first type. Zhang et al.~\cite{zhang2025b} distill the utility judgments of a 32-billion-parameter teacher LLM into smaller student models, and Sandhu et al.~\cite{sandhu2026} retrain the retriever’s embedding model with complex objectives so that its ranking follows utility. Both reach utility-aware selection, but at the cost of heavy training, and the former also needs a large teacher model to produce its supervision, which is hard to afford under low-budget conditions. Learned rerankers and selection policies trained from utility feedback form the second. LURE-RAG introduces a lightweight LambdaMART reranker trained with a listwise utility loss~\cite{chandra2026}, while RRPO treats passage selection as a sequential decision process optimized by reinforcement learning from LLM feedback~\cite{wu2026}. LURE-RAG depends on expensive query-passage labeling, and RRPO consumes substantial memory and computation.

Utility estimation by directly involving the target LLM is the third. Zhang et al.~\cite{zhang2025c} run the target LLM twice for every query to compare its behavior with and without the passage, and SePer measures how much the semantic perplexity changes once the passage is provided~\cite{dai2025}. Methods of this type are closest to the definition of utility as improvement over the model’s internal memory, but they add inference cost and latency at selection time, so they are less suitable for real-time use. Lightweight utility predictors form the fourth. Perez-Beltrachini and Lapata~\cite{perez2025} propose a lightweight neural model that predicts utility for a target QA model, yet it is trained for one specific model and is difficult to transfer to others. Tian et al.~\cite{tian2026} combine Query Performance Prediction (QPP), perplexity, readability, and document quality features in a linear regression, which is cheap but reaches only Spearman $\rho \approx 0.20$--$0.24$ for retrieval utility on Natural Questions.

MPUP is compared to eight previous studies which were based on six criteria, presented in Table~\ref{tab:mpup_positioning}. C1 is a lightweight model that runs on limited hardware. C2 is no fine-tuning of the LLM or the retriever. C3 is no additional LLM run for every query at selection time. C4 is utility estimation accuracy that is competitive with methods that probe the target LLM directly. C5 is a single predictor that works for several target LLMs without retraining. C6 is training on annotations that already exist in the dataset instead of labels generated by the target LLM.

Table~\ref{tab:mpup_positioning} shows how the studies differ. Methods that reach high accuracy through the target LLM~\cite{zhang2025c,dai2025} fail the lightweight and per-query cost criteria, while lightweight methods~\cite{perez2025,tian2026} either remain tied to one model or lose accuracy. LURE-RAG~\cite{chandra2026} is the one study that reports reusing a predictor, trained on the utilities of one LLM, for other LLMs (its fourth research question), but its labels come from running an LLM. MPUP meets C2 by design. MPUP still runs an LLM at selection time (one short generation per query and one probing pass per passage), so it meets C3 only in part, and its memory use meets C1 in 4-bit precision, where the full pipeline peaked at 6.4 GiB on a laptop. For C4--C6 this paper gives only partial evidence. All partial marks are shown as $\sim$ in the table.

Utility-based selection is only useful if people can actually run it. Many practitioners have access to only a single GPU and a limited budget, not a training cluster. Methods that need very large models, retriever retraining, or two LLM runs for every query are out of reach for them. Methods that are cheap but tied to one LLM create another problem, because the predictor must be rebuilt whenever the LLM is replaced. Lightweight methods with low accuracy are also not helpful, since they often pick the wrong passages. Every barrier above would be removed by a predictor that is lightweight and does not have to be rebuilt for each new LLM, provided that its ranking is good enough to help. MPUP is designed for this purpose by combining many cheap features into one predictor, and Section~IV measures how good its ranking is.

\section{Methodology}
Fig.~\ref{fig:mpup_overview} shows the MPUP pipeline. For each query, MPUP first asks an
LLM $M$ to write one short hypothetical answer. Then, for every
candidate passage, it extracts 14 features from five feature families.
Next, the trained regressor maps these features to a utility score, and an
optional calibration step adjusts the scale of the score. Passages are ranked by the score, and the top passages are placed in the prompt
of the target LLM. No fine-tuning of the target LLM is ever needed, and the question does not need to be answered twice for every passage.


Passage utility measures whether a passage, given as evidence, improves
the accuracy of an LLM compared with answering without any evidence~\cite{zhang2026}. Let $q$ be query, $d$ candidate passage, and $L$
target LLM. Utility of $d$ for $L$ on query $q$ is the difference
in generation accuracy~\cite{zhang2026}:

\begin{equation}
    u(d;L,q)
    =
    \operatorname{Acc}(L(q,d))
    -
    \operatorname{Acc}(L(q,\varnothing)).
    \label{eq:utility}
\end{equation}

Where $L(q,\varnothing)$ is the answer of $L$ from its own memory alone,
and $L(q,d)$ is the answer of $L$ when it reads $d$.
$\operatorname{Acc}(\cdot)$ is a standard correctness metric. Passage
is useful only if reading it improves the model, which means $u>0$.
Zero utility means the passage adds nothing, and a negative value
means it makes the answer worse.

If we test a pool of candidate passages $\mathcal{C}$ in this way and
keep only the passages that help $L$, we obtain the gold utilitarian
set of $L$~\cite{zhang2026}:

\begin{equation}
    \widetilde{\mathcal{G}}_q^{(L)}
    =
    \{d \in \mathcal{C} \mid u(d;L,q)>0\}.
    \label{eq:gold}
\end{equation}

$\operatorname{Acc}$ is the average of relaxed exact match and
token-level F1 against the gold answers:

\begin{equation}
    \operatorname{Acc}(a)
    =
    0.5 \cdot \operatorname{EM}_r(a)
    +
    0.5 \cdot \operatorname{F1}(a).
    \label{eq:acc}
\end{equation}

Relaxed exact match counts an answer as correct when a gold answer
appears inside it as a token span. Relaxed matching is used because instruction-tuned
LLMs answer in full sentences, and strict exact match would mark most
of them wrong, which pushes almost every utility to zero. Values of $u$ lie in $[-1,1]$.

Building $\widetilde{\mathcal{G}}$ directly needs two LLM runs for
every query-passage pair, which is too expensive for real-time
selection. MPUP predicts the utility instead, so that passages in
$\widetilde{\mathcal{G}}$ are ranked first:

\begin{equation}
    \hat{u}(d;q)
    =
    f_{\theta}(\phi(q,d;M)),
    \label{eq:pred}
\end{equation}

where $\phi(q,d;M)\in\mathbb{R}^{14}$ is the feature vector and
$f_{\theta}$ is the predictor. $M$ is the LLM used for the two
LLM-based steps, the hypothetical answer and logit probing. Either the target LLM $L$ or a fixed model can serve as $M$. In our experiments, $M$ is
Qwen2.5-7B-Instruct. Predictor $f_{\theta}$ is trained once and is not retrained when $L$ changes.

Table~\ref{tab:mpup_features} lists the 14 features. D1 describes how the retriever
scored the passage: its BM25 score (divided by the highest score of
the query), its dense similarity, its rank, and its score gap to the
next passage. D2 describes the passage itself: token length,
Flesch--Kincaid grade, and a source credibility score. D3 measures
meaning overlap. Entity overlap is the fraction of query entities,
found by spaCy, that also appear in the passage. Answerability is the
fraction of content words of the hypothetical answer that appear in
the passage. D4 checks faithfulness with a DeBERTa-v3-small NLI model.
Here, the passage is the premise and the hypothetical answer is the hypothesis, and we keep the entailment and contradiction probabilities.
D5 probes the LLM $M$. Next-token entropy is computed at the end of two prompts: the query alone
($H_{\text{base}}$) and the passage followed by the query
($H_{\text{ctx}}$). D5 features are the two perplexities $\exp(H)$
and the difference
$\Delta H = H_{\text{base}} - H_{\text{ctx}}$. Generated once per query, the hypothetical answer is shared by D3 and D4.

Standardized features are passed to a regressor. Two kinds are considered. One kind, the reference configuration, is a gradient-boosted regression tree model (200 trees, depth 5, learning rate 0.05, subsample 0.8) trained on
the raw features. Another kind trains on within-query deviations: the
mean of the query is subtracted from every feature and from the label
before fitting, and at inference the candidates of the query being ranked
form that group. Much of the raw utility is an offset per query
(a question that the LLM already answers makes every passage useless),
which no reranker can use. Centred models spend no capacity on it, and their scores mean ``better or worse than the average candidate''. The
configuration is chosen from a grid of twelve (ridge regression with three
regularization strengths and gradient-boosted trees of three sizes, each
with and without centring) by nested leave-one-dataset-out, described in
Section IV.

Two kinds of label are used. In the main experiments the predictor is
trained on the true utility \eqref{eq:utility} of the training datasets.
When no LLM labels are wanted, it can instead be trained on labels derived
from existing annotations. RAGBench marks which sentences of each document were used to produce
the answer. For passage $d$, the label is the fraction of its sentences that are marked:

\begin{equation}
    \tilde{u}(d)
    =
    \frac{|S_d \cap S_{\text{used}}|}{|S_d|},
    \label{eq:proxy}
\end{equation}

where $S_d$ is the set of sentences of $d$ and $S_{\text{used}}$ is
the set of marked sentences. No LLM is run to produce these labels.
True utility \eqref{eq:utility} is computed with the same LLM $M$ acting
as the source LLM. Generated once per query, the no-context answer is reused for all passages of that query.

Optionally, $\hat{u}$ can be calibrated when labels from the target
LLM are available for $k$ passages. Coefficients $\alpha$ and $\beta$ are fitted by linear regression on these $k$ examples, and the calibrated score is

\begin{equation}
    \hat{u}' = \alpha \cdot \hat{u} + \beta.
    \label{eq:calib}
\end{equation}

Calibration changes the scale of $\hat{u}$, which matters for the threshold
$\tau$. Rankings do not change as long as $\alpha > 0$,
because the order of the scores stays the same. Calibration is not
used in the main results.

Both LLM-based steps, hypothetical answer generation and logit probing, share one model $M$: Qwen2.5-7B-Instruct, run in bfloat16 on
a single NVIDIA RTX 6000 Ada GPU (48 GB). Sharing one copy avoids
loading a second 7B model, and full-precision weights mean that no
quantization error enters the probing and generation steps. Alternatively, the implementation can load $M$ in 4-bit NF4 with double
quantization to reduce memory; we report peak memory for both settings
in Section IV. Also available is an Apple Silicon backend that uses a 4-bit Llama-3.2-3B-Instruct through
MLX. Both the NLI model and the regressor are small and run without
quantization.

At inference time, MPUP makes one short greedy decode per query (at
most 48 tokens) for the hypothetical answer. For each passage it makes
one probing pass and one NLI pass, then applies the regressor. Passages are sorted by score, and the top $m$ ($m = 5$ by default)
are written as numbered context before the query. Dropping passages with a score $\leq \tau$ is also supported. With the selected
predictor, which is trained on within-query deviations, the score is
relative to the other candidates of the same query, so $\tau = 0$
would drop roughly the less useful half of the candidates rather than
the passages with negative utility. No threshold is therefore applied.
Neither choice is evaluated by answer accuracy in this paper.

\subsection{Evaluation protocol}
All metrics are computed within each query and then averaged over queries, because a reranker can only order the passages of one query. Queries are used when they have at least two passages and their true utilities are not all equal (747 of the 1,100 queries with gold answers). Spearman correlation $\rho$ between the predicted score and the true utility serves as the main metric. Intervals are 95\% percentile bootstrap intervals over queries (2,000 resamples), and differences between methods are paired on the same queries. Splits are always by query, never by row.

Three kinds of numbers appear and should not be confused. The \emph{effect} is the paired difference $\Delta\rho$ between MPUP and a baseline (or $\Delta\mathrm{Acc}$ for answer accuracy): larger is better, zero means no gain. The \emph{evidence} is the two-sided $p$-value of H$_0$: $\Delta=0$, reported next to a 95\% interval: smaller is better, and $p<0.05$ (after Holm correction when several datasets are tested) means that a difference of zero is unlikely, while an interval that excludes zero says the same thing. The \emph{size} of the effect is the standardised $d_z=\bar{\Delta}/s_{\Delta}$ over queries: larger is better, with about 0.2 small and 0.5 medium. Even a tiny $p$ can accompany a tiny effect when there are many queries, so all three are given.

Because the predictor is chosen from data, its score is estimated with nested leave-one-dataset-out. One dataset is held out. Among the other ten, each of the twelve configurations is scored by leave-one-dataset-out and the best is kept. Refitted on those ten datasets, the best configuration is scored on the held-out one, whose labels are not used for the choice. Choosing the best configuration on the held-out dataset itself would have reported $\rho=0.357$, which is 0.024 above the nested estimate. Since the grid was designed after an earlier run on the same questions with a smaller 3B model had shown that the reference configuration was weak, even the nested estimate is slightly optimistic. Results without any selection are also reported for the reference configuration.

\subsection{Setup}
Two runs share the questions, the candidate passages, the labels' definition, and the protocol. The main run uses one Apple M5 laptop with 24 GiB of unified memory and MLX: Qwen2.5-7B-Instruct in 4-bit precision serves as LLM $M$. The earlier run used the same model in bfloat16 on one NVIDIA RTX 6000 Ada GPU and is kept as a comparison (Tables~\ref{tab:main} and~\ref{tab:ablation} and Fig.~\ref{fig:forest}). Model $M$ writes the hypothetical answer, produces the probing features and the hidden states, and acts as the source LLM that defines the true utility (greedy decoding, at most 32 new tokens, relaxed exact match). The two runs differ in precision, hardware, and therefore also in labels, so their numbers are not interchangeable. Multilingual-E5-large provides the dense feature and the dense baseline. Baselines are BM25 and dense cosine similarity used alone as ranking scores.

\paragraph{Significance tests (GPU run)} Whether MPUP orders passages better than dense similarity is tested as a hypothesis. H$_0$: the mean within-query difference in $\rho$ between MPUP and dense similarity is zero. H$_1$: it is not zero (two-sided, $\alpha = 0.05$). Queries are the units, and the differences are paired. Per-query values are bounded and not normally distributed, so the $p$-values are recovered from the paired bootstrap intervals of Table~\ref{tab:main} as in a paired $t$-test: $t = \hat{\delta}/\mathrm{SE}$ with $n-1$ degrees of freedom, where $\mathrm{SE}$ is the interval width divided by 3.92. The intervals are close to symmetric (asymmetry at most 0.08), and against exact sign-flip permutation tests on the earlier Llama run the approximation differs by at most 0.03 in $p$. Holm's correction covers the eleven single-dataset tests, and the pooled test is one test (the $p$-values are listed in Tables~\ref{tab:main} and~\ref{tab:ablation}). Over all 747 held-out queries, H$_0$ is rejected ($p = 0.001$, standardised effect $d_z = 0.12$). Per dataset, H$_0$ is not rejected after correction in any dataset: SQuAD ($p = 0.005$, Holm 0.058) and MuSiQue ($p = 0.014$, Holm 0.14) come closest, and the other nine datasets give no evidence of a difference. On the fresh questions with the frozen configuration, H$_0$ is rejected as well ($p < 0.001$, 693 queries). Rejecting H$_0$ means that a difference of zero is unlikely, not that the difference is large: the mean gain is +0.04 in $\rho$ and the standardised effect is small. Datasets of 44 to 94 queries each detect only a difference of about 0.06 to 0.17 in $\rho$ at 80\% power, so failing to reject H$_0$ there does not show equal performance.

Retriever features (D1) matter most. Because the check uses the same datasets, transfer to new datasets is not tested, and Bamboogle contributes only 6 fresh questions.

\subsection{Cost}
Table~\ref{tab:memory} gives the peak GPU memory of the full pipeline (generation, labelling, probing, and NLI), measured on the datasets with the longest contexts (40 questions from MuSiQue and HotpotQA, batch size 32). Labelling and feature extraction for all twelve datasets (9,554 query--passage pairs, 7,997 of them labelled with the true utility) took 27 minutes in bfloat16 on one GPU, about 0.17 s per pair. On the laptop, the same extraction with the 4-bit model, including two layers of hidden states per pair, took 2.9 hours (10,466 s, about 1.1 s per pair) at batch size 8, and the peak memory over the whole run was 6.4 GiB of unified memory. Evaluation itself runs on the CPU. Over the whole extraction run for the second sample of questions (all twelve datasets), the peak in bfloat16 was 22.3 GiB. The behaviour on a card or laptop with 8 GB of memory was not measured.

\subsection{Limitations}
Results use one source LLM per run and 100 questions per dataset (390 for RAGBench). One sample of questions underlies the main estimate, and the second sample checks it only for a frozen configuration on the same datasets, so the intervals reflect the variation among questions, not among models. Because true utility is defined by the same LLM $M$ that produces the D5 features, whether a predictor trained with one source LLM ranks passages well for a different target LLM has not been tested. Answer accuracy was measured only for $m=1$ and $m=3$ and only with the LLM $M$ that also defines the utility, so whether the gain carries over to another answering LLM is open. The hidden-state probe and the grid of variants were designed after the baseline run on the same questions, so the nested estimates are slightly optimistic, and the configuration has not yet been scored once on a new sample of questions. Extraction time above includes the labelling with the true utility; the latency of selection alone (one generation per query, then probing, NLI, and the regressor per passage) was not measured. The probing prompt (passage, then query) is truncated at 512 tokens from the right, so for 35 of the 9,554 pairs (0.37\%) the query is cut off and their D5 features are computed without it. Candidate sets are small (4 to 20 passages), and in the datasets without provided passages they are the top five of BM25, which limits how much any reranker can change.

\section{Conclusion}
MPUP is a predictor of the utility of a retrieved passage for an LLM that combines 14 inexpensive features and a probe on the hidden states of the LLM, and it does not fine-tune the target model. Run end to end on a laptop with a 4-bit 7B model (6.4 GiB peak), it ranks passages across eleven datasets with a within-query Spearman correlation of 0.37 against 0.28 for dense similarity, a paired gain of +0.08 (p $<$ 0.001, $d_z=0.22$). The gain comes from the hidden-state probe; the 14 features alone gain +0.02, which is not significant. Placing the top passage in the prompt raises answer accuracy by 5.4 points over dense similarity, a quarter of the distance to a perfect ranker. Future work should confirm the configuration on a new sample of questions, test transfer between source and target LLMs, measure the latency of selection alone, and evaluate on datasets that are not in the pool.
